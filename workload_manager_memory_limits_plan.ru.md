### 1.2 Закомментированный throw в `dq_compute_memory_quota.h` — результаты расследования

`dq_compute_memory_quota.h:143-147`: при отказе `AllocateQuota()` в лог записывается только предупреждение; стоящий ниже `throw yexception()` закомментирован.

**История (прослежена до источника во внутренней Arcadia).** Строка появилась закомментированной — она никогда не была рабочим кодом:

  - Источник: arc commit `b825db9aba3e` (svn r6988105, imakunin, 2020-06-19), KIKIMR-9865 «дозапрашивать память для mkql программ в процессе выполнения», ревью <https://a.yandex-team.ru/review/1304556>, изначально в `kikimr/core/kqp/compute_actor/kqp_compute_actor_impl.h`.
  - В том же коммите появились `SetIncreaseMemoryLimitCallback` + `TryIncreaseLimit` в `yql/minikql/aligned_page_pool.*`, переписавшие существовавшие до этого типизированные точки throw на схему «превышен лимит → вызвать callback → всё равно превышен → throw `TMemoryLimitExceededException`». Контракт callback с самого начала: отказ сигнализируется тем, что лимит *не поднимается*; исключение бросает пул.
  - В ревью 1304556 также зафиксирована дискуссия о семантике статуса, релевантная D4: spuchin настаивал, что отказ — это `PRECONDITION_FAILED`; imakunin оставил ошибку выполнения («в зависимости от размещения данных запрос может как завершиться успешно, так и завершиться неудачей») — нынешний `OVERLOADED`.
  - Тикет KIKIMR-9865 подтверждает намерения: автор назвал изменение прототипом («этот код скорее прототип»), а vvvv одобрил синхронный callback-дизайн («да понятно, синхронный callback. Нормально»). Закомментированный throw — остаток этой прототипной стадии.
  - Исходная фича также имела режим блокирующего ожидания (`EnableInstantMkqlMemoryAlloc`, ожидание до `InstantMkqlMemoryAllocWaitTimeMs` =20 мс с поллингом каждые 1 мс, затем MemoryLimitExceeded). Позднее он был удалён — поля 8-10 помечены как `reserved` в `ydb/core/protos/table_service_config.proto:36-38`. Сейчас отказ — мгновенный. Если D5 (пауза со спиллингом перед kill) возвращает ожидание, оно должно быть асинхронным, а не старым поллинг-циклом (черновик дизайна: потоки исполнителей никогда не блокируются на памяти).
  - Код попал в публичный репозиторий уже закомментированным при импорте февраля 2022 (`1110808a9d3`) и был дословно перенесён в `dq_compute_memory_quota.h` коммитом `d4d446c9c53` (YQ-833, апрель 2022).

**Почему закомментированный throw безопасен (и правилен).** Применение ограничений происходит на уровень ниже. `RequestExtraMemory` вызывается из `TAlignedPagePool::TryIncreaseLimit()` (`yql/essentials/minikql/aligned_page_pool.cpp:685-691`), которая после callback проверяет `Limit_ >= required`; если квота была отклонена, лимит не поднят, `TryIncreaseLimit` возвращает false, и страничный пул бросает типизированное исключение `TMemoryLimitExceededException` (`aligned_page_pool.cpp:400,448,546`). Compute actors ловят именно этот тип и завершают запрос с `OVERLOADED` / «Mkql memory limit exceeded». Обобщённый `yexception`, брошенный внутри callback, *обошёл бы* эту классификацию и всплыл бы как INTERNAL\_ERROR — что заведомо хуже. Существующие тесты `KqpLimits::ComputeActorMemoryAllocationFailure[QueryService]` (`ydb/core/kqp/ut/query/kqp_limits_ut.cpp:291,315`) проверяют цепочку «отказ → типизированное исключение → `OVERLOADED`» сквозным образом для узлового лимита; оба были перезапущены на текущем транке (2026-07-25) и проходят («Mkql memory limit exceeded», статус OVERLOADED, код 2029).

**Последствия для плана:**

  - НЕ раскомментировать throw — вместо этого удалить мёртвый закомментированный код, добавив комментарий со ссылкой на применение ограничений в page-pool (небольшой PR-cleanup).
  - Применение ограничений для compute-страниц работает сегодня; реальные проблемы — *что поступает на вход отказа* (именованные пулы не учитывают ExternalMemory, обход нулевого процента, устаревший конфиг) и *что вообще не проходит через квоту* (см. 1.3.6).
  - Любое изменение семантики отказа (например, добавление паузы для спиллинга перед падением или ужесточение отказа для именованных пулов) является изменением поведения и ДОЛЖНО вводиться под фиче-флагом, по умолчанию выключенным, с предварительным введением observe-only счётчиков. Ничего в этой области нельзя менять «простым раскомментированием».
  - Оставшийся тонкий момент, заслуживающий теста: `UpdateMemoryYellowZone()` подавляется, пока установлен `IncreaseMemoryLimitCallback_` и флаг максимального лимита не достигнут (`aligned_page_pool.cpp:672`), поэтому давление для спиллинга при управляемых выделениях исходит только от `IsReasonableToUseSpilling()` (куки RM `SpillingPercent`), а не от локальной жёлтой зоны пула.

### 1.3 Прочие находки, не отражённые в черновике дизайна

1.  **`QUERY_MEMORY_LIMIT_PERCENT_PER_NODE` отвергается при валидации.** `ydb/core/resource_pools/resource_pool_settings.cpp:74-76` возвращает «not supported yet» для любого значения, отличного от -1. Включение лимитов на запрос требует снятия этой валидации и проработки совместимости при rolling upgrade.

2.  **Memory Controller не имеет потребителя KQP.** `EMemoryConsumerKind` (`ydb/core/base/memory_controller_iface.h:7-18`) содержит только кэш, memtable и CS-потребителей. Бюджет выполнения запросов передаётся в виде лимита очереди Resource Broker: `GetQueryExecutionLimitBytes()` → `TEvResourceBroker::TEvConfigure` на `KqpResourceManagerQueue` (`memory_controller.cpp:446-501`); потребление наблюдается через `TAlignedPagePool::GetGlobalPagePoolSize()`. Корневой лимит узла арбитра должен точно отслеживать лимит очереди RB через `TotalMemoryResource`, что уже реализовано посредством `TEvConfigResponse` (`kqp_rm_service.cpp:768`). Новый потребитель Memory Controller для шагов 1–6 не нужен.

3.  **Мониторинг памяти по пулам полностью отсутствует.** `MemoryNamedPools` нигде не экспортируется: страница мониторинга RM показывает только узловые итоговые показатели (`kqp_rm_service.cpp:875-922`), whiteboard публикует одну устаревшую запись. Развёртывание в режиме observe-only невозможно до тех пор, пока не появятся счётчики.

4.  **Дерево планировщика CPU напрямую расширяемо, но имеет проблемы с временем жизни.** `TStaticAttributes` (`runtime/scheduler/tree/common.h:33-38`) хранит только `Weight/CpuLimit/CpuGuarantee/ReadLimit`. Конфигурация пула доходит до планировщика по полностью переиспользуемому пути: pool handler SchemeCache watch → `NWorkload::TEvUpdatePoolInfo` → `TComputeSchedulerService` (`kqp_compute_scheduler_service.cpp:140-186`). Однако `TEvRemoveDatabase`/`TEvRemovePool` — это `Y_ABORT("Unsupported yet")` (`kqp_compute_scheduler_service.cpp:100-101,136-137`) — время жизни memory account не должно зависеть от удаления из дерева до реализации этого функционала.

5.  **Хук управляемых выделений уже существует и работает пакетно.** `IMemoryQuotaManager` (`dq_compute_actor_async_io.h:39`) является единственным синхронным шлюзом для роста compute-heap; запросы выравниваются до 1 МиБ с минимальным чанком 30 МиБ (`MinMemAllocSize`) и гистерезисом сжатия 30 МиБ. Буферы каналов проходят через второй экземпляр (`TChannelQuotaManager`, `kqp_query_control_plane.cpp:78`). Такая пакетная обработка ограничивает конкуренцию на горячем пути арбитра по замыслу — блокировка иерархии на запрос ≥1 МиБ приемлема; lock-free дерево поначалу не требуется.

6.  **Пробелы в покрытии текущей квоты.** Покрыто: страницы MKQL, Arrow через `OffloadAlloc` (при `EnableArrowTracking`), буферы каналов. Не покрыто: путь `UseDefaultArrowAllocator()`, буферы итераторов stream-lookup (ad-hoc лимиты типа `MaxTotalBytesQuotaStreamLookup`), буферы write-actor в полёте (`InFlightMemoryLimitPerActorBytes`), а также все начальные резервирования `ExternalMemory` на уровне именованных пулов.

7.  **Разводка тегов tcmalloc сквозная и легко расширяема.** TLS-тег (`ydb/library/actors/prof/tcmalloc.cpp`) → сэмплированное выделение `user_data` через `SetSampleUserDataCallbacks` → счётчики сэмплов по тегам с `MaxTag = 2048` (`ydb/core/mon_alloc/tcmalloc.cpp:672-694`). Исполнитель устанавливает тег равным *типу активности* актора только при смене активности (`executor_thread.cpp:272-277`). Составной тег (activity, pool) укладывается в лимит 2048, если теги пулов интернированы; per-query теги исключены (неограниченная кардинальность). Только для сэмплирования — никогда для применения ограничений.

8.  **Путь сигнала спиллинга готов и учитывает пулы.** `TTxState::IsReasonableToStartSpilling()` (`kqp_rm_service.h:88-91`) читает куки спиллинга как по узлу, так и по пулу; флаг поступает в `TAlignedPagePool::SetMaximumLimitValueReached()` после каждого запроса сверх квоты. `SpillingPercent` глобален для узла; пороги на пул были бы новым поведением.

9.  **`TCpuQuotaManager` — не переиспользуемая модель** (подтверждает черновик): это кластерный шлюз допуска на основе EMA для `DATABASE_LOAD_CPU_THRESHOLD`, а не механизм справедливого разделения ресурсов.

### 1.4 Уточнённое архитектурное решение

Предложение черновика «арбитр памяти рядом с планировщиком CPU» сохраняется, с уточнениями:

  - **Переиспользовать как есть:** типы идентификаторов (`TDatabaseId/TPoolId/TQueryId`, `runtime/scheduler/fwd.h`), поток подписки на конфиг пула (`TEvSubscribeOnPoolChanges` / `TEvUpdatePoolInfo`) и паттерн жизненного цикла `TEvAddQuery`/`TEvRemoveQuery`.
  - **Не переиспользовать:** снимок математики fair-share, вычисление задержки, шлюз CAS-on-`CpuUsage` — память это занятость, а не скорость.
  - **Расположение:** новая библиотека `ydb/core/kqp/rm_service/memory_arbiter/`, потребляемая `TKqpResourceManager`; переход в отдельный сервис только тогда, когда шаги с actor-context потребуют его за пределами KQP.
  - Обобщённые интерфейсы `NActors::NMemory` из черновика появляются только в Шаге 8, когда они потребуются runtime акторов; более ранние шаги остаются внутри KQP.

### 1.5 Обзор предшествующих решений — принятые идеи

В `workload_manager_memory_prior_art.md` рассмотрено десять систем (ClickHouse, CockroachDB, TiDB, Velox, DuckDB, DataFusion, Trino/Presto, Impala, SQL Server, Greenplum). Сходящиеся выводы, влияющие на данный план:

  - **Отказ первому обратившемуся на уровне узла — нетипичный дизайн.** Все рассмотренные системы разрешают давление на уровне узла через выбор жертвы (наиболее превысивший гарантию или крупнейший потребитель), ограниченное ожидание или арбитраж — не отказом запросу, выделяющему ресурс следующим. YDB в настоящее время работает по принципу «первый обратившийся» как на уровне пула, так и на уровне узла. → рекомендации R1/R2.
  - **Гарантия + лимит на пул** (знаменатель перекоммита ClickHouse, фиксированные и разделяемые уровни Greenplum, MIN/MAX\_MEMORY\_PERCENT SQL Server) — стандартная модель данных, при которой ранжирование жертв (`used / guarantee`) хорошо определено. → R1, включено в Шаг 5/11.
  - **Эскалирующая цепочка действий при отказе** (TiDB: throttle → спиллинг → отмена; ожидающее состояние Trino; resource semaphore SQL Server): сначала спиллинг и сжатие, затем ограниченное асинхронное ожидание, в последнюю очередь типизированная ошибка. → R3, включено в Шаг 6.
  - **Шлюзы допуска на резервировании, а не на потреблении** (Impala; Trino softMemoryLimit ставит новые запросы в очередь и никогда не убивает выполняющиеся). → R4, включено в Шаг 11.
  - **Оценка гранта + обратная связь по перцентилям** (адаптивные гранты SQL Server). → R5, новый follow-up тикет.
  - **Арбитраж как конечное состояние** (Velox SharedArbitrator: освобождение свободной квоты → команда спиллинга по reclaimable bytes → прерывание крупнейшего): проектировать интерфейсы Шага 5 так, чтобы reclaim можно было добавить без ломающих изменений. → R6.
  - Дешёвая диагностика, принятая на раннем этапе: аннотация топ-потребителей в каждом сообщении об отказе (DataFusion TrackConsumersPool), дампы при pre-OOM давлении и история аудита kill/deny (TiDB). → R9, в Шаги 2 и 9.
  - Антипаттерны для избежания, с upstream-примерами: зарезервированный пул Presto (удалён как ошибка дизайна, trino\#6677); memory-aware throttling *выполняющейся* работы как замена допуска (примечания по допуску CockroachDB: это может увеличить занятую память).

### 1.7 Внутренняя зонная модель (hor911, sbr://13145352241) — выравнивание

Внутренняя презентация «О самом дорогом — памяти» определяет целевую лестницу
зрелости и модель управления на каждом уровне, с которой должен быть согласован
данный план:

- **Лестница зрелости:** нет лимитов → жёсткие лимиты (отказ) → **жёлтая зона**
  (спиллинг; «мы здесь» — путь куки `SpillingPercent`, зафиксированный тестами
  Шага 1) → **красная зона** (асинхронное высвобождение/вытеснение памяти) →
  минимальные лимиты + планируемое выполнение.
- **Модель PUSH/PULL на каждом уровне:** контейнер PUSHит лимиты (и пороги
  green/yellow/red) вниз к компонентам; компонент PULLит изменения лимитов
  от своего контейнера. Сопоставление: Memory Controller — N/A; Resource
  Broker — PUSH; KQP RM — PULL; **WM Resource Pool — PUSH(?); Query —
  PUSH(?)**; Task — PULL. Данный план разрешает два вопросительных знака: аккаунты
  пула и запроса получают лимиты через PUSH от конфига, принадлежащего подписке
  (Шаг 4), и от арбитра (Шаг 5), тогда как задачи продолжают PULLить через
  `IMemoryQuotaManager`.
- **Зонная семантика, принятая в арбитр (Шаг 5):** каждый уровень аккаунта
  имеет пороги green/yellow/red. Жёлтый проверяется синхронно при увеличении
  лимита (PULL) и отказывает в «необязательном» росте — это сегодняшний
  `IsReasonableToStartSpilling`, обобщённый на уровне аккаунта. Красный
  инициирует асинхронный reclaim — компонент возвращает память «когда сможет,
  сколько сможет» — что является точной спецификацией контракта reclaim D12/R6;
  семантика красной зоны теперь конкретизирует этот контракт.
- **Upstream-зависимости в ведении трека hor911** (данный план их потребляет,
  а не реализует): светофор RB→RM (флаги зон, передаваемые из Resource Broker),
  и фикс Memory Controller для распределения >100% (перекоммит) в любой
  конфигурации. Отслеживаются как координационные follow-up.

**Последовательность (согласована):** ограничение пулов на уровне узла
выходит первым — Шаги 1–6 по замыслу строго локальны для узла. Ограничение
пулов/запросов на уровне кластера приходит позже, через предложение zverevgeny:
workload manager потребляет **gossip-распределённое** потребление по пулам
(существующий `TKqpResourceInfoExchanger` уже gossip-ит снимки ресурсов узла —
`ResourceSnapshotState` в `kqp_rm_service.cpp`). Агрегаты с конечной
согласованностью неточны для коротких запросов (окно устаревания ≈ период
обменника), но достаточны для длинных запросов, доминирующих по памяти —
короткие запросы управляются только локальными узловыми лимитами. См. Шаг 13
и D13.

## 3\. Пошаговый план

Порядок «сначала тесты»: каждое изменение поведения предваряется тестами, фиксирующими текущее поведение, а каждое изменение применения ограничений выходит под фиче-флагом, по умолчанию выключенным.

### Шаг 1 — Написание недостающих тестов (фиксация текущего поведения)

Изменений в production-коде нет. Каждый тест документирует сегодняшнюю семантику; тесты, выявляющие проблему, утверждают *текущее* (дефектное) поведение с комментарием, ссылающимся на шаг исправления, и переключаются PR этого шага.

1a. `kqp_rm_service/kqp_rm_ut.cpp` — добавить pool-aware перегрузку `MakeTx`; тесты:

  - два именованных пула на одном узле, изоляция между ними;
  - одно имя пула в двух базах данных (ключ — `(database, pool)`);
  - пул с нулевым процентом → в настоящее время обходит учёт пула (зафиксировать; исправляется в Шаге 4);
  - неограниченный (-1) пул;
  - ALTER во время выполнения: старая транзакция восстанавливает устаревший процент через `SetNewLimit` (зафиксировать; исправляется в Шаге 4);
  - выделение только ExternalMemory никогда не затрагивает именованный пул (зафиксировать; исправляется в Шаге 4);
  - откат при отказе Resource Broker после резервирования пула (`Y_DEFER` в `kqp_rm_service.cpp:330-346`);
  - конкурентные acquire/release в одном именованном пуле;
  - куки спиллинга пула переключаются на пороге `SpillingPercent`.

1b. `yql/essentials/minikql/ut/aligned_page_pool_ut.cpp` — контракт `IncreaseMemoryLimitCallback` сегодня не тестируется:

  - callback поднимает лимит → выделение проходит;

1c. `ydb/core/kqp/ut/query/kqp_limits_ut.cpp` / `ydb/core/kqp/workload_service/ut` — сквозные тесты именованных пулов:

### Шаг 4 — Исправление корректности именованных пулов (с фиче-флагами, где видно пользователю)

  - **Владение конфигом:** RM подписывается на обновления пула как планировщик CPU (`TEvSubscribeOnPoolChanges` → `TEvUpdatePoolInfo`) и становится единственным писателем лимитов пулов. `TTxState` теряет `MemoryPoolPercent`; `SetNewLimit` на пути транзакции удаляется. Записи пулов живут столько, сколько подписка, а не до usage==0.
  - **Семантика нулевого процента** согласно D2, под фиче-флагом (изменение поведения: сегодня ноль отключает принудительное применение).
  - **ExternalMemory списывается на пул** согласно D6, под тем же флагом: node service передаёт идентификатор пула с начальными резервированиями (`kqp_query_control_plane.cpp:323-329`); удаляется обход раннего возврата при `Memory==0` в `kqp_rm_service.cpp:258-264`.
  - **Горячий путь D6 — lock-free, одна атомарная RMW-операция на запрос** (дизайн на основе бенчей, см. отчёт §3.2/§3.4): хэндл аккаунта пула разрешается один раз при регистрации транзакции и кэшируется в `TTxState`; alloc/free = `pool->ExternalUsed.fetch_add/sub` (relaxed). Уровень запроса использует существующий атомик `TxExternalDataQueryMemory`; агрегаты по БД/узлу выводятся с каденсом публикации (`FireResourcesPublishing`), а не per-op — узловой атомик покидает горячий путь. Если D6 в будущем потребует применения ограничений (а не только атрибуции): оптимистичный `fetch_add` + сравнение с лимитом + откат (паттерн ClickHouse, R7) с задокументированным ограниченным перерасходом ≤ количество параллельных запросов в полёте. Полностью выводит OLTP-запросы (чьё единственное взаимодействие с RM — этот путь) из под блокировочных конвоев RM. **Измерено (прототип, 2026-08-09)**: внешний путь 58 нс vs 54 нс baseline (заблокированный MVP — 215 нс); цикл OLTP 259 нс vs 206 нс baseline (MVP 368 нс) — +53 нс — это однократное разрешение хэндла на запрос. Прототип: `bench_patches/d6_lockfree.patch` на ветке `bench/memory-baseline` (paste: <https://paste.yandex-team.ru/3fea8b2d-c10e-451b-b0ad-c9d2585ce131/text>).
  - **Три отдельных фиче-флага**, а не один: (a) отклонение нулевого процента (D2, видимое пользователю изменение семантики), (b) списание ExternalMemory на пул (D6, новый источник отказа для пулов с превышением лимита), (c) владение конфигом (внутреннее, минимальный риск). Разные радиусы поражения должны независимо откатываться.
  - Записи пулов — это refcounted хэндлы, спроектированные для принятия в `TMemoryAccountTree` Шага 5 без повторной инициализации — никакой второй миграции времени жизни.
  - Переключить зафиксированные тесты из Шага 1a.

### Шаг 5 — Выделение библиотеки арбитра памяти

`ydb/core/kqp/rm_service/memory_arbiter/` + ut:

  - `TMemoryAccountTree`: аккаунты узел → база данных → пул → запрос; атомарный многоуровневый `TryAcquire`/`Release` с полным откатом; одна блокировка на запрос приемлема (батчинг ≥1 МиБ, находка 1.3.5).
  - Refcounted хэндлы аккаунтов с состоянием `Closed` (принимает освобождения, отказывает в выделениях — выделения переживают запросы).
  - Обновление лимитов на любом уровне; снижение ниже текущего использования только запрещает рост.
  - API снимков для счётчиков/мониторинга.
  - `TKqpResourceManager` делегирует: `TotalMemoryResource` → аккаунт узла, `MemoryNamedPools` → аккаунты пулов. Взаимодействие с RB не изменяется.
  - Unit-тесты: применение иерархии, откат, стресс-тест на потоках, динамические лимиты, закрытие с непогашенными байтами, насыщение.
  - Дополнения из prior-art (R1/R2/R6/R12): аккаунты содержат `{guarantee, limit}` согласно D10, а не просто лимит; снимок включает `ReclaimableBytes` на запрос (0 до тех пор, пока Шаг 7 потребители не начнут его сообщать) и флаг `NonReclaimable`; вспомогательная функция `RankVictims()` упорядочивает запросы по (приоритет пула, used/guarantee, размер) для пути давления на узле; события deny/kill записываются в кольцевой буфер аудита, доступный на странице мониторинга RM.

  - Пороги зон на аккаунт (green/yellow/red, §1.7): жёлтый обобщает куку спиллинга и проверяется при acquire; красный инициирует асинхронное событие reclaim, зарезервированное D12. Пороги PUSHатся вместе с лимитом владельцем конфига.
  - Добавить `MEMORY_GUARANTEE_PERCENT_PER_NODE` в `TPoolSettings`, proto и DDL (задание D10) — только модель данных на этом шаге; применение является задачей триггера Шага 11.
  - Масштабирующий шлюз (DoD, из отчёта §3.4): перезапустить `rm_alloc_free_named_pool_contended{4,16,32}` на бинарнике арбитра; Δp50 ≤ +5% к транку на каждом уровне параллелизма.

### Шаг 6 — Лимиты на запрос

  - Снять валидацию в `resource_pool_settings.cpp:74-76` под фиче-флагом (D9); распространить через `kqp_planner.cpp` → `kqp_node_service.cpp` вместе с процентом пула.
  - Аккаунт запроса при регистрации транзакции; лимит = эффективный лимит пула × процент (D3); все выделения проверяются на уровне запроса.
  - Отказ следует цепочке эскалации (R3, паттерн TiDB/Trino): (1) установить хинт спиллинга и повторить; (2) `TryShrinkMemory` (освободить свободные страницы, снизить лимит) и повторить; (3) за флагом D11 — зарегистрироваться как ожидающий памяти в арбитре, ограниченное асинхронное ожидание, пробуждение через `FreeQuota` от завершающихся запросов; (4) завершиться с ошибкой статуса D4 и сообщением, называющим пул/лимит **и топ-N потребителей пула в момент отказа** (R9). Терминальная ошибка остаётся типизированным `TMemoryLimitExceededException`, никогда не `yexception`.
  - Пороги спиллинга — отношения к *эффективному* (наиболее ограничивающему) лимиту в цепочке — грант запроса vs лимит пула vs бюджет узла — пересчитываются при изменении грантов (R8, паттерн ClickHouse PR \#71406), а не в абсолютных байтах.
  - Статистика уровня запроса в proto статистики запроса (пик, отказано, спиллинг, лимит, пул) — не динамические счётчики (кардинальность).
  - Когда D11 выключен, цепочка явно (1)→(2)→(4) — стадия ожидания пропускается, а не деградирует молча; бюджет D5 всё равно ограничивает весь эпизод.
  - Управление бурями (§13.3): состояние эскалации на запрос в `TTxState`/аккаунте запроса запоминает, что spill/shrink уже не удался в этом эпизоде — последующие отказы сразу переходят к своей стадии вместо повторного прохождения цепочки на каждый запрос в 1 МиБ.
  - **DoD содержит флаг «частичное покрытие»**: до выхода Шагов 7–9 лимиты покрывают только выделения MKQL/Arrow/channel; write-path память не отслеживается, и лимиты по пулам НЕ ДОЛЖНЫ рекламироваться как защита от OOM на узле.
  - Тесты: лимит на запрос ниже/выше лимита пула; много запросов в одном пуле; multi-node запрос, применяющий ограничение локально на каждом узле — включая то, что локальный отказ фрагмента распространяет отмену на дочерние фрагменты на других узлах через существующий путь прерывания KQP.

### Шаг 6a — Шлюз допуска на основе памяти (KR2, вынесен вперёд из Шага 11)

  - Резерв `min_grant` до тикета #16 (обратная связь по перцентилям): консервативная статическая оценка, по умолчанию 10% от лимита пула, настраивается через конфиг. Проверка допуска — быстрое чтение атомика, без round-trip к актору.
  - Тесты: пул на лимите → новый запрос встаёт в очередь; выполняющийся запрос завершается → запрос из очереди допускается; очередь ограничена `QUEUE_SIZE`; observe-only режим считает would-be-queued без реального помещения в очередь.

### Шаг 11 — Взвешенный допуск по памяти (приоритизация)

Да «приоритизировать память как CPU» — но как *право на новый рост* (отказ/спиллинг/отмена заёмщиков), а не мгновенное изъятие.

  - По D7/D10: права пулов из весов над бюджетом узла, выраженные парой guarantee/limit; заимствование разрешено между guarantee и limit; right < usage → запрет роста, давление спиллинга, отмена по ранжированию жертв (R2), никогда не мгновенное изъятие.
  - Шлюз допуска по памяти (R4, семантика Impala/Trino): допуск workload service проверяет `pool.reserved + initial_grant ≤ pool.limit`, где `reserved` учитывает принятые, но ещё не использованные гранты (резервирование ≠ потребление); при превышении мягкого лимита → новые запросы встают в очередь существующей FIFO пула; выполняющиеся запросы никогда не убиваются при допуске.
  - Начальный грант сначала статический (из D3); follow-up тикет добавляет обратную связь по перцентилям из пиковой статистики памяти по форме запроса (R5, адаптивные гранты SQL Server).
  - Периодический пересчёт в арбитре (каденс как у `UpdateFairShare`), а не в коде снимков CPU.
  - **Триггер защиты пола (делает гарантию D10 реальной)**: когда использование узла > Σ гарантий, новые выделения из пулов с `used > guarantee` отклоняются/ставятся в очередь, пока пулы с `used < guarantee` продолжают получать гранты. Без этого правила гарантия — лишь модель данных без эффекта.
  - `initial_grant` до тикета #16: наследует статический `min_grant` из Шага 6a; документировать, что grant=0 делает проверку только постфактумной (фаза observe).
  - Тесты (DoD): инкремент/декремент reserved при admit/complete; очередь → разблокировка при завершении; защита пола — пул ниже гарантии продолжает выделять, пока заёмщик выше гарантии получает отказ; проверка допуска < 2 мкс на операцию (бенч-шлюз).
  - Если предпочтительно разделение дерева: сначала реализовать `TEvRemovePool`/`TEvRemoveDatabase` в сервисе планировщика (находка 1.3.4).

### Шаг 12 — Точное отслеживание на уровне аллокатора (отдельный трек)

Без изменений относительно черновика: только прототип, под build/runtime флагом, со своими бенч-шлюзами. Входные данные для решения берутся из измерений остатка в Шаге 10.

### Шаг 13 — Кластерные лимиты пулов/запросов через gossip (после стабилизации per-node)

Согласно последовательности §1.7: только после выхода Шагов 1–6 (per-node) в
продакшн. Механизм (дизайн zverevgeny):

- Расширить существующие снимки `TKqpResourceInfoExchanger` данными об
  использовании по пулам (ограниченная кардинальность: только пулы, никогда
  per-query).
- Workload service / арбитр потребляют gossip-агрегат для применения бюджетов
  пулов и ограничений на запрос на уровне кластера: только решения о допуске
  и правах — никакой синхронной кластерной координации на горячем пути выделения.
- Задокументированный контракт точности (D13): ошибка применения ограничена
  окном устаревания gossip × совокупная скорость выделения; короткие запросы
  могут завершиться за одно окно и намеренно управляются только локальными
  узловыми лимитами. Длинные запросы сходятся к кластерному ограничению.
- Тесты: двухузловой runtime (по паттерну существующих тестов обменника),
  длинный запрос, ограниченный кластерным бюджетом при наличии свободного
  узлового бюджета; короткий burst под-применяется, но ограничен; недоступность
  обменника деградирует до локального узлового применения (fail-open, счётчики
  сигнализируют устаревание).

Вердикт по OLTP: MVP примерно удваивает *стоимость жизненного цикла OLTP-запроса на стороне RM*, однако в абсолютных числах это +160 нс на запрос (p99 389 нс) — на фоне согласованных E2E-бюджетов (1–3 мс точечные чтения/записи, ~10 мс распределённые транзакции) это 0.01–0.04%. Стоимость RM на запрос не является OLTP-риском, а lock-free дизайн D6 (Шаг 4) устраняет даже эту дельту вместе с lock-convoy-связанностью.

Находка по масштабируемости (предсуществующая, НЕ вызванная MVP — дельты в пределах ±2% шума на каждом числе потоков): текущий путь lock+ResourceBroker-instant не масштабируется. Задержка на операцию растёт линейно с числом потоков (2 мкс → 27.8 мкс ×4 → 139 мкс ×16 → 287 мкс ×32), то есть совокупная пропускная способность *обваливается* с ~500 kops/s однопоточно до ~110 kops/s при 32 потоках (блокировочный конвой + пинг-понг строк кэша). Последствия для плана:

  - Арбитр Шага 5: оставить единственную блокировку только вместе с батчингом ≥1 МиБ (находка 1.3.5); добавить микробенч-шлюз в DoD Шага 5: не допускать регрессии этой кривой.
  - Если частота обращений к RM когда-либо вырастет (меньшие чанки, больше вызывающих — например, расширение покрытия в Шаге 7), сначала должно выйти шардирование блокировок по пулам или relaxed-атомики per-pool; внешнее списание D6 — первый кандидат для перехода на lock-free атомики per-pool.
  - Числа при 32 потоках ограничивают худший случай для OLTP-всплесков: даже при полном насыщении блокировки один цикл RM для OLTP-запроса стоит ~0.3 мс — заметно, но только под синтетическим 32-поточным штормом выделений.

## 6\. Критерии успеха и риски

Критерии успеха как в черновике дизайна, плюс:

  - Включение флага Шага 4 ничего не меняет для пулов без настроек памяти.
  - Шаг 3 вообще ничего не меняет (доказывается тестами Шага 1).

Дополнения к реестру рисков относительно черновика:

  - **Унаследованное ужесточение применения:** пулы, которые сегодня молча превышают свой процент (через обход ExternalMemory / нулевой процент), могут начать падать при включении флага Шага 4. Смягчение: observe-only счётчик «WouldBeDeniedBytes» из Шага 2 до любого включения флага.
  - **Время жизни записей пулов:** удаление нулевых записей (`kqp_rm_service.cpp:400-404`) конфликтует с конфигом, принадлежащим подписке — подписка становится владельцем; следить за пулами, удалёнными во время выполнения запросов.
  - **Соблазн переиспользовать дерево планировщика:** дерево не поддерживает удаление (`Y_ABORT` в `kqp_compute_scheduler_service.cpp:100,136`); не связывать время жизни memory account с ним до реализации этого функционала.
  - **Исключения неправильного типа:** любой новый путь отказа должен бросать `TMemoryLimitExceededException` (или подкласс), никогда не обобщённый `yexception`, иначе сломается маппинг статусов compute-actor (см. 1.2).
  - **Слепое пятно ingest-масштаба (обзор §13):** до выхода Шагов 7–9 высокоскоростная write-память (буферы interconnect, очереди write-actor, insert/compaction columnshard) невидима аккаунтам пулов — per-pool лимиты могут выглядеть зелёными, пока узел OOM-ится при ~300 МБ/с ingest. Не рекламировать шлюз допуска как защиту от OOM узла до покрытия write-path; страховочная сеть уровня узла (R2) должна опираться на вид всего процесса от Memory Controller, а не на сумму аккаунтов пулов.
  - **Инварианты масштаба быстрого пути и пути давления (обзор §13):** каждый учитываемый путь должен выполнять acquire в единицах ≥размера чанка с actor-local батчингом (трафик к арбитру остаётся ~10²/с даже при 300 МБ/с); любое ожидание должно быть приостановкой mailbox, никогда не блокированным потоком; сети на основе поллинга нуждаются в headroom ≥ `ingest_rate × (poll interval + cancel latency)`; эпизоды deny/victim/waiter нуждаются в storm control (пакетные упорядоченные пробуждения, один kill на эпизод, per-query-память о провалившихся стадиях эскалации).
