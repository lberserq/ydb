# Workload Manager Memory Limits — отчёт о бенчмарках и выводы по решениям

Статус: отчёт по измерениям, 2026-08-09. Сопровождает `workload_manager_memory_limits_plan.md` (решения D1–D12, шаги 1–12) и `workload_manager_memory_limits_design.md`.

Цель: **насколько MVP-реализация предложенных дефолтных значений деградирует задержки, потребление памяти и масштабируемость по сравнению с текущим trunk** — данные для защиты дефолтов или их возврата на более детальное обсуждение.

## 1\. Что измерялось

### 1.1 Baseline

Upstream trunk `bb228c7f4c0` (2026-08-09), без изменений. Набор бенчмарков и прототипные патчи зафиксированы в ветке `bench/memory-baseline` (черновой PR: <https://github.com/lberserq/ydb/pull/3>); сами RM-прототипные патчи никогда не применяются в зафиксированном виде — они живут как файлы `bench_patches/*.patch`.

### 1.2 MVP дефолтных значений решений

Прототипный патч из 146 строк к `ydb/core/kqp/rm_service/kqp_rm_service.cpp` (`bench_patches/mvp_rm.patch` в ветке `bench/memory-baseline`, патч: <https://paste.yandex-team.ru/c2a7f06c-eabb-4466-8af1-8183a22daaf8/text>), аппроксимирующий стоимость горячего пути для дефолтов плана:

  - **4-уровневый учёт** (D3/D10, шаг 5): учётная запись уровня базы данных `TMemoryResource`, захватываемая/освобождаемая под существующей блокировкой RM в дополнение к node + pool — node → database → pool → query.
  - **Проверка лимита на запрос** (D3, шаг 6): одна атомарная загрузка + сравнение с лимитом запроса, вычисленным из лимита пула, при каждом выделении.
  - **Тарификация ExternalMemory в пул** (D6, шаг 4): текущий lock-free путь ExternalMemory (два атомика) дополнительно захватывает блокировку RM и выполняет acquire/release для учётных записей пула и базы данных.
  - **Записи пула, принадлежащие подписке** (шаг 4 / 1c): нет удаления при обнулении; конфигурация пула не перезаписывается из состояния транзакции (`SetNewLimit` убран из tx-пути).

Семантика отказов не изменена; лимиты установлены так, чтобы в бенчмарках ничего не отклонялось — измеряется только накладная стоимость учёта.

### 1.3 Бенчмарки

Набор юнит-тестов `KqpRmBench` (`ydb/core/kqp/rm_service/kqp_rm_bench_ut.cpp` в ветке `bench/memory-baseline`), реальный `TKqpResourceManager` + ResourceBroker в тестовом акторном рантайме:

| Бенчмарк                                      | Исполняемый путь                                                                                            |
| --------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `rm_alloc_free_no_pool`                       | Alloc+free 1 MiB, без resource pool — **контроль**: код идентичен в обоих бинарниках                        |
| `rm_alloc_free_named_pool`                    | То же, tx привязана к именованному пулу (50%)                                                               |
| `rm_alloc_free_external_only`                 | Резервирование только ExternalMemory (путь первоначальных резервирований task/channel)                       |
| `rm_oltp_query_cycle`                         | Полный жизненный цикл RM для небольшого запроса: создание tx → 1×(ExecutionUnits+ExternalMemory) alloc → free → уничтожение tx |
| `rm_alloc_free_named_pool_contended{4,16,32}` | N потоков, каждый со своей tx, один пул — масштабируемость блокировки                                       |
| `mkql_churn_{plain,callback}_limit`           | Смешанный churn страничного пула MKQL: задержка + фрагментация, огромный лимит vs жёсткий лимит с callback выдачи |

### 1.4 Протокол

  - Перемежающийся A/B: бинарники base и MVP чередуются для каждого теста в каждом раунде — дрейф нагрузки на машину компенсируется в сравнении.
  - Итоговый датасет (v3): **20 раундов × 100 внутрипроцессных итераций × 2000 операций/итерацию** → 2000 сэмплов на (тест, вариант); медианы перцентилей по вызовам между раундами.
  - Хост: 57 ядер, нагрузка ≈ 1.3 в начале, ≈ 4 во время (сами бенчмарки); метки нагрузки на раунд записаны в сырой лог.
  - Уровень шума для контрольного пути: **p50 +1.9%, p95 +0.4%, p99 −0.6%** — дельты менее \~2% являются шумом.
  - Сырые логи: `baseline_bench.log`, `ab_bench_v2.log`, `ab_bench_v3.log`, агрегат `v3_agg.json` (рабочее пространство сессии).

## 2\. Результаты (v3, финальные)

Пара alloc+free, если не указано иное; нс на операцию.

| Бенчмарк            | base p50 | mvp p50 | Δp50      | Δp95   | Δp99               |
| ------------------- | -------- | ------- | --------- | ------ | ------------------ |
| no pool (контроль)  | 1849     | 1883    | \+1.9%    | \+0.4% | −0.6%              |
| named pool          | 2023     | 2146    | **+6.1%** | \+4.4% | \+1.6%             |
| ExternalMemory-only | 54       | 213     | **+294%** | \+268% | \+269%             |
| OLTP query cycle    | 207      | 366     | **+77%**  | \+73%  | \+71% (p99 389 ns) |
| contended ×4        | 27 824   | 27 770  | −0.2%     | \+0.1% | \+1.5%             |
| contended ×16       | 138 841  | 141 693 | \+2.1%    | \+2.6% | \+2.8%             |
| contended ×32       | 287 025  | 284 619 | −0.8%     | −0.6%  | −0.7%              |

Страничный пул MKQL (MVP не затрагивает): \~120 нс/оп задержки churn; callback увеличения лимита добавляет \~5%; после освобождения половины блоков пул удерживает все страницы (retained/used ≈ 2×) до shrink/`ReleaseFreePages` — фрагментация контролируется существующим гистерезисом сжатия в 30 MiB, а не арбитром.

### 2.2 Реальные нагрузки: TPC-C / TPC-H на выделенных узлах (2026-08-13)

Бинарники: trunk `88ad64bac2e` (`ydbd_base`, sbr:13145518395) против того же trunk
с включённым lock-free учётом D6 для каждого запроса и дефолтным
бюджетом 128 GB (`ydbd_memlimits`, sbr:13145836999, diff sbr:13145838107) — проверки выполняются
при каждом выделении, но никогда не отказывают: чистая стоимость ведения учёта.

- **TPC-C** (6000 складов, 1 ч): tpmC 40 177 → 39 889 (−0.72%, один прогон,
  в пределах разброса между запусками); p50 *улучшился* на один бакет гистограммы для 4/5
  типов транзакций, p99 вырос на один бакет; 0 неудачных транзакций в обоих.
- **TPC-H**: геометрическое среднее по запросам −1.42% (memlimits быстрее), медианное соотношение
  ≈ 1.000; разброс по запросам ±20% в обе стороны (вариативность кэша/компакции).
  memlimits: 0 отказов, 0 расхождений результатов (в базовом прогоне было 4 отказа).
- Результаты: base tpcc sbr:13165919805, base tpch sbr:13165925249, memlimits
  tpcc sbr:13165933990, memlimits tpch sbr:13165935710.

Повторный прогон (2026-08-14, тот же бинарник memlimits, sbr:13182284137): tpmC
38 138, геометрическое среднее TPC-H −0.15% против base. **Разброс между запусками одного бинарника: TPC-C ±4.4%,
геометрическое среднее TPC-H ±1.3%** — все наблюдаемые дельты base↔memlimits лежат внутри
разброса одного бинарника, и накладные расходы не обнаружимы с корректными
планками погрешностей. Следствие: данная конфигурация TPC-C не позволяет разрешить дельты ниже ~5% в
одном прогоне (дрейф окружения между прогонами — накопленное состояние данных/компакции);
сравнения по уровням требуют ≥3 повторений или сброса состояния между прогонами.
4 отказа запросов TPC-H повторяются независимо от бинарника (base: 4, memlimits
прогон 1: 0, прогон 2: 4) — нестабильность нагрузки/окружения.

Оговорка об эффективных лимитах (из телеметрии кластера): Memory Controller
продавливает собственный лимит выполнения запросов в очередь RB (~7.2 GiB/узел на
данном сегменте), перекрывая дефолтное значение RM proto — пиковое потребление составило ~12% от
бюджета, поэтому эти прогоны проверяют только ведение учёта, без принуждения к лимитам. Многоуровневый
план (control/yellow/deny/htap через pool DDL, скрипт sbr:13168531079)
покрывает принуждение.

Вывод: учёт, включённый по умолчанию, не измерим на масштабе реальных нагрузок;
дельты микробенчмарков (§2) не проявляются на end-to-end уровне. Оптимизация горячего пути OLTP
остаётся работой на улучшение, а не предусловием.

## 3\. Выводы

### 3.1 Стоимость учёта дефолтов — шум на фоне роста

Alloc+free с именованным пулом прибавляет \~123 нс (+6.1%) на проверку запроса + учётную запись базы данных. Этот путь выполняется один раз на chunk квоты — выравнивание 1 MiB, минимум 30 MiB (`MinMemAllocSize`) — то есть на каждые 30 MiB реального роста памяти добавленная стоимость составляет \~0.1 мкс. Невидимо ни на каком перцентиле задержки запроса.

### 3.2 Тарификация ExternalMemory (D6) — единственный структурно более медленный путь

54 → 213 нс (\~4×): lock-free путь из двух атомиков становится lock + два поиска в map + два acquire (×2 для free). Абсолютная стоимость +159 нс на резервирование, на частоте старта задачи / шага канала 1 MiB.

**Решается lock-free вариантом (проверен 2026-08-09, `bench_patches/d6_lockfree.patch`, патч: <https://paste.yandex-team.ru/3fea8b2d-c10e-451b-b0ad-c9d2585ce131/text>, 10-раундовый трёхсторонний перемежающийся прогон):** дескриптор учётной записи пула разрешается один раз на tx (кэшируется в `TTxState`), тарификация на операцию — один relaxed `fetch_add` на учётную запись пула; агрегаты db/node вычисляются с периодичностью публикации. Измерено: внешний путь **58 нс** (base 54, MVP с блокировкой 215); цикл OLTP **259 нс** p50 / 328 нс p99 (base 206/227, MVP 368/383) — остаточные +53 нс — это однократное разрешение дескриптора на запрос. Тарификация внешней памяти более не затрагивает блокировку RM вообще.

### 3.3 OLTP: стоимость RM на запрос удваивается — до 366 нс

Полный жизненный цикл RM для запроса OLTP-формы составляет 207 → 366 нс p50 (p99 389 нс). По отношению к бюджету E2E даже в 1 мс это 0.04%; к 10 мс — 0.004%. Лёгкий OLTP-запрос обращается к RM ровно один раз и никогда не входит на путь инкрементального роста. **Стоимость RM на запрос не является риском для OLTP.**

### 3.4 Реальная проблема существовала до MVP: путь блокировки RM не масштабируется

Задержка на операцию при конкуренции растёт линейно с числом потоков в **обоих** вариантах (base ≈ MVP в пределах шума):

| Потоки | p50 на операцию | суммарная пропускная способность |
| ------- | ---------- | -------------------- |
| 1       | \~2 мкс    | \~500 kops/s         |
| 4       | \~28 мкс   | \~144 kops/s         |
| 16      | \~139 мкс  | \~115 kops/s         |
| 32      | \~287 мкс  | \~111 kops/s         |

Суммарная пропускная способность *падает* \~4.5× от 1 до 32 потоков (lock convoy + cache-line ping-pong на блокировке RM + мгновенные вызовы ResourceBroker). MVP не добавляет ничего измеримого к насыщенной блокировке. Сегодня это маскируется 30 MiB-чанкингом; граница остаётся комфортной — даже при полном насыщении один цикл RM для OLTP-запроса стоит \~0.3 мс — но батчинг несёт нагрузку.

| D3 проверка на уровне запроса (лимит относительно пула)       | **Защитить** — одна атомарная проверка, входит в дельту +6.1% named-pool                                                                                       | §3.1     |

| Шаг 5 однозамковый арбитр                                     | **Защитить, с новым условием** — приемлемо только совместно с батчингом ≥1 MiB; добавить gate отсутствия регрессии по кривой масштабируемости §3.4 в определение готовности шага 5 | §3.4     |
