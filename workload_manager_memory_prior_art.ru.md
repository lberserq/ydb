# Prior art: управление памятью внутри процесса в монолитных СУБД

Дополнение к `workload_manager_memory_limits_plan.md`. Обзор того, как другие базы данных и движки запросов управляют памятью *внутри одного процесса*, с выводами о том, какие механизмы стоит перенять для лимитов памяти воркload-менеджера YDB. Источники — публичная документация и исходный код соответствующих проектов; ссылки приведены непосредственно в тексте по каждой системе.

Исходное состояние YDB для сравнения (см. план, §1.4): вычислительные акторы получают квоту через `IMemoryQuotaManager` → `TKqpResourceManager` (узловой `TotalMemoryResource` + именованные счётчики на пару (database, pool)), MKql `TAlignedPagePool` применяет выданный лимит через callback увеличения лимита, а отказ выражается в типизированном `TMemoryLimitExceededException`, который вычислительный актор преобразует в `OVERLOADED`. Admission выполняется в workload service на уровне ресурсного пула; сегодня память не участвует в admission.

## 1\. ClickHouse

Ближайший аналог YDB: монолитный C++-бинарник с собственной обёрткой аллокатора, полной атрибуцией памяти по процессу и (недавно добавленными) SQL-определяемыми воркloadами.

### 1.1 Иерархия MemoryTracker с TLS-батчингом

Цепочка родителей: thread-local счётчик → `MemoryTracker` запроса → трекер пользователя → серверный `total_memory_tracker`. Каждый `new`/`delete` проходит через аллокатор ClickHouse, вызывающий `CurrentMemoryTracker::alloc()/free()`; дельты накапливаются в TLS-счётчике и сбрасываются вверх лишь при превышении `max_untracked_memory` (4 МБ по умолчанию), поэтому стоимость одной аллокации — это TLS-прибавка, а атомарные операции и проверки лимита срабатывают раз в \~4 МБ. Потоки привязываются к `ThreadGroupStatus` запроса (который владеет трекером запроса), так что многопоточные запросы агрегируются естественно. С 2025 года (PR \#84082) даже сторонний C-`malloc` перехватывается через linker `--wrap`. Кэши (mark cache, словари) явно учитываются на серверном трекере; метаданные jemalloc и tcache остаются неотслеживаемыми (дрейф RSS, §1.4).

### 1.2 Применение лимитов

Проверка лимита происходит внутри трекера при сбросе: `current + delta > limit` → бросается `DB::Exception` с кодом 241 `MEMORY_LIMIT_EXCEEDED`, в сообщении указывается уровень срабатывания («for query» / «for user» / «total»). Лимиты: `max_memory_usage` (10 ГБ по умолчанию на запрос), `max_memory_usage_for_user`, `max_server_memory_usage(_to_ram_ratio)` (0.9 от RAM).

### 1.3 Memory overcommit: гарантии и выбор жертвы вместо отказа первому же обратившемуся

Начиная с версии 22.5. При включённом overcommit лимиты на запрос становятся мягкими; жёсткий потолок — это серверный лимит. При его достижении запрашивающий запрос не падает сразу:

1.  Он *ждёт* в `OvercommitTracker` (до `memory_usage_overcommit_max_wait_microseconds`).
2.  Трекер выбирает жертву: запрос с наибольшим отношением `allocated / memory_overcommit_ratio_denominator` — то есть тот, кто больше всего превысил свою *гарантированную* долю. Denominator = 0 означает, что запрос никогда не станет жертвой (защищённые запросы).
3.  Жертва отменяется; если за отведённое время освободится достаточно памяти, ожидающий запрос возобновляется, иначе он получает исключение 241.

Ключевая семантика: denominator — это **грант памяти** на уровне запроса/пользователя, и давление разрешается против того, кто больше всего превысил гарантию, — а не против того, кто просто аллоцировал последним.

### 1.4 Сверка jemalloc/RSS: MemoryWorker и cgroup observer

Фоновый цикл `MemoryWorker` обновляет статистику эпох jemalloc, вычисляет объём dirty-страниц и очищает арены, когда dirty > 10 ГиБ или > 20% от отслеживаемой памяти; PR \#94902 разделил его на быстрый поток обновления RSS и медленный поток очистки, чтобы задержки очистки не влияли на корректировку лимитов. `CgroupsMemoryUsageObserver` читает cgroup v2 `memory.current` (исправлено для исключения переиспользуемого page cache после issue \#64652) и корректирует `total_memory_tracker`. Наблюдаемый разрыв: async-метрики `MemoryResident` − `MemoryTracking`; `SYSTEM JEMALLOC PURGE` закрывает его вручную.

### 1.5 Воркloadы: память как планируемый ресурс (экспериментально)

`CREATE RESOURCE memory (MEMORY RESERVATION)` + `CREATE WORKLOAD ... SETTINGS max_memory = '10Gi'` + `reserve_memory` на уровне запроса: резервирование запроса находится в состоянии *pending* до тех пор, пока у воркloada не появится свободное место (очередь допуска), затем — *running*; под давлением выполняющиеся резервирования могут быть вытеснены (запрос убивается) в порядке воркloadа `precedence`, по принципу max-min fair по весу внутри уровня. Сосуществует с (не заменяет) жёсткими лимитами MemoryTracker; merge/mutation пока не охвачены. Планирование CPU и I/O в том же дереве воркloadов продвинулось дальше (token buckets, вытесняющие CPU-слоты).

### 1.6 Спиллинг, привязанный к эффективному лимиту

`max_bytes_ratio_before_external_group_by/sort`: порог вычисляется как `ratio × min(лимит запроса, пользователя, сервера)` путём обхода цепочки трекеров (PR \#71406), поэтому точки спиллинга автоматически масштабируются с конфигурацией, а не задаются в абсолютных байтах.

Ключевые ссылки: `src/Common/{MemoryTracker,OvercommitTracker,MemoryWorker,CgroupsMemoryUsageObserver}.*`, <https://clickhouse.com/docs/operations/settings/memory-overcommit>, <https://clickhouse.com/docs/operations/workload-scheduling>, <https://github.com/ClickHouse/ClickHouse/issues/84976> (umbrella воркloadов), <https://github.com/ClickHouse/ClickHouse/issues/41887> (предложение по reclaimable memory).

## 2\. CockroachDB

### 2.1 Дерево BytesMonitor / BoundAccount (`pkg/util/mon`)

Каноническая Go-реализация иерархического дерева учёта:

  - **Иерархия**: корневой монитор (узловой, ограничен `--max-sql-memory`, по умолчанию 25% RAM) → монитор сессии (на соединение) → монитор запроса/потока → монитор оператора. Бюджет дочернего монитора — это сам `BoundAccount`, открытый против родителя, поэтому списания распространяются вверх.
  - **Амортизированное резервирование**: `BoundAccount.Grow()` сначала расходует локально пред-зарезервированный буфер и обращается к родителю только кусками размером `poolAllocationSize` (10 КБ по умолчанию), освобождая излишки при превышении 10 кусков. Это снижает конкуренцию за блокировку на общем корне.
  - **Отказ — это значение ошибки**, а не callback: `"memory budget exceeded"` распространяется к оператору; векторизованный движок преобразует его во внутреннюю панику, перехватываемую на границах операторов.
  - **Разделение спиллинга и отказа**: мягкий бюджет на оператор `sql.distsql.temp_storage.workmem` (64 МиБ по умолчанию) инициирует сброс на диск (external sort, grace hash join и т.д. через Pebble temp storage); *узловой глобальный* бюджет `--max-sql-memory` не имеет fallback-спиллинга — его исчерпание означает жёсткую ошибку запроса в целях защиты узла.
  - **Off-heap кэши**: блочный кэш Pebble (`--cache`, 25% RAM) намеренно аллоцируется вне Go heap через CGo malloc, чтобы GC его не видел; он бюджетируется при запуске, а не отслеживается на аллокацию.

### 2.2 Контроль допуска (admission control) явно исключает память

Admission control в CockroachDB (очереди слотов/токенов, упорядоченные по tenant → priority → tx start time) управляет только CPU и I/O хранилища. В технических заметках прямо указано, почему память исключена: память невытесняема, и замедление некоторых уровней может лишь *ухудшить* ситуацию, продлевая удержание уже аллоцированной памяти. Backpressure по памяти целиком живёт в дереве BytesMonitor. Это важное предупреждение для YDB: ограничение *выполняющейся* работы с учётом памяти — это другая задача, нежели *admission* с учётом памяти, и первое может дать обратный эффект.

Ключевые ссылки: `pkg/util/mon/bytes_usage.go`, `pkg/sql/colmem/allocator.go`, `docs/tech-notes/admission_control.md`, <https://www.cockroachlabs.com/blog/disk-spilling-vectorized/>, <https://www.cockroachlabs.com/blog/memory-usage-cockroachdb/>.

## 3\. TiDB

### 3.1 Дерево MemTracker и цепочка эскалации OOMAction

На сессию/исполнитель — дерево `MemTracker` (`util/memory`); `Consume()` обходит предков и, когда любой узел превышает лимит, запускает **цепочку эскалирующих действий** этого узла (связный список, каждый элемент имеет указатель на fallback):

1.  `rateLimitAction` — сначала снизить параллелизм: остановить один конкурентный поток сканирования таблицы (`tidb_enable_rate_limit_action`).
2.  Действия спиллинга — специфичные для оператора: `SpillDiskAction` (hash/merge join), `SortAndSpillDiskAction`, `AggSpillDiskAction` (переключает HashAgg в режим спиллинга).
3.  Терминальное действие — `PanicOnExceedAction` (CANCEL, по умолчанию: запрос отменяется с разбивкой по памяти на оператор в сообщении об ошибке) или `LogOnExceedAction` (LOG: продолжить, только залогировать). Конфигурируется через `tidb_mem_oom_action`.

Мягкий бюджет на запрос: `tidb_mem_quota_query` (1 ГиБ по умолчанию).

### 3.2 Глобальный контроллер памяти: убийство наибольшего потребителя

Начиная с v6.5: `tidb_server_memory_limit` (по умолчанию 80% RAM). Фоновая горутина опрашивает Go `HeapInuse`; при превышении лимита она раз за разом убивает сессию с наибольшим отслеживаемым потреблением до возврата ниже лимита (DDL и некоторые классы запросов освобождены). События убийства доступны для аудита через `INFORMATION_SCHEMA.MEMORY_USAGE_OPS_HISTORY` (последние 50 событий: timestamp, SQL digest, память).

### 3.3 Аварийный сигнал давления с диагностическими дампами

`tidb_memory_usage_alarm_ratio` (по умолчанию 0.7): при пересечении порога (ограничено одним разом в минуту и только при росте потребления >10%) TiDB сохраняет дампы стеков горутин, heap profile и топ-10 запросов по памяти/длительности в ротируемые файлы — диагностика захватывается *до* OOM, а не после.

### 3.4 Сверка с аллокатором и рантаймом

gctuner корректирует `GOMEMLIMIT`/частоту GC относительно серверного лимита; контроллер читает `HeapInuse`, принимая как данность, что стеки и метаданные рантайма не отслеживаются. Та же история, что у CockroachDB: ни одна из Go-систем не сверяет отслеживаемые байты с RSS полностью; они ограничивают то, что могут, и оставляют запас.

Ключевые ссылки: <https://docs.pingcap.com/tidb/stable/configure-memory-usage/>, <https://pingcap.github.io/tidb-dev-guide/understand-tidb/memory-management-mechanism.html>, `util/memory/tracker.go`, `util/gctuner/memory_limit_tuner.go`.

## 4\. Meta Velox (используется в Prestissimo / Presto C++)

С архитектурной точки зрения наиболее интересный дизайн для YDB: память **арбитрируется между выполняющимися запросами**, причём предпочтительный способ — reclaim через спиллинг, а не отказ с ошибкой.

### 4.1 Дерево MemoryPool с логической ёмкостью, отдельной от физической аллокации

Дерево пулов на запрос, отражающее дерево выполнения (корневой пул запроса → task → node → operator; только листовые пулы взаимодействуют с физическим аллокатором). Каждый корневой пул запроса имеет текущую логическую `capacity_`, которую арбитр может увеличивать/уменьшать в реальном времени, и жёсткий `maxCapacity_`, зафиксированный при старте запроса. Физическая аллокация (`MemoryAllocator`) и логический бюджет (`MemoryArbitrator`) — это разные уровни; ёмкость можно перемещать между запросами без касания страниц.

### 4.2 SharedArbitrator: алгоритм growCapacity

Когда резервирование превысит ёмкость запроса, пул просит арбитра увеличить её. Алгоритм, сериализованный под глобальным мьютексом:

1.  **Self-check**: если запрашивающий уже достиг своего `maxCapacity`, попытаться self-reclaim (спиллинг собственных операторов); если всё равно превышение — локальный отказ (без жертв).
2.  **Быстрый путь**: отобрать *свободную* ёмкость (зарезервированную, но неиспользуемую) у других запросов через `shrink()` — чисто бухгалтерская операция, без I/O.
3.  **Медленный путь**: отсортировать кандидатов по `reclaimableBytes()` (оценка spillable-состояния) и скомандовать им выполнить reclaim: reclaimer запроса → reclaimer task'а (приостанавливает драйверы task'а) → `Operator::reclaim()`, который сбрасывает хеш-таблицы / прогоны сортировки / состояние window на диск. *Арбитр* инициирует спиллинг, а не оператор.
4.  **Крайняя мера**: `handleOOM()` прерывает запрос с **наибольшей текущей ёмкостью** и повторяет попытку. Потоки-запрашиватели «входят в арбитраж» в приостановленном состоянии, чтобы их собственный task мог быть приостановлен для reclaim без дедлока.

Операторы помечают `nonReclaimableSection_` вокруг критических фаз (например, в процессе построения хеш-таблицы); арбитр пропускает их.

### 4.3 Примечательные свойства

  - Выбор жертвы основан на ёмкости, а не на приоритете (уровни приоритетов обсуждались выше по течению, но не были реализованы) — пробел, который могут заполнить ресурсные пулы YDB.
  - Спиллинг инициируется извне, поэтому политика сосредоточена в одном месте; операторы реализуют только механизм (`reclaim()` + `reclaimableBytes()`).

Ключевые ссылки: <https://facebookincubator.github.io/velox/develop/memory.html>, <https://facebookincubator.github.io/velox/develop/spilling.html>, `velox/common/memory/{MemoryPool,MemoryArbitrator,SharedArbitrator}.h`.

## 5\. DuckDB

### 5.1 Унифицированный buffer manager

Один глобальный `memory_limit` (по умолчанию 80% RAM) управляет *всей* памятью — страницами хранилища и промежуточными результатами операторов — в блоках по 256 КБ с семантикой pin/unpin и LRU-вытеснением в `temp_directory`. Операторы не пишут код спиллинга: они *unpin'ят* блоки, а buffer manager прозрачно вытесняет их под давлением. Политика спиллинга полностью отделена от логики операторов.

### 5.2 TemporaryMemoryManager: переговоры между параллельными операторами

Решает задачу «два hash join, каждый размером 60% лимита → 120%». Операторы с интенсивным потреблением памяти регистрируют `TemporaryMemoryState` (RAII), объявляют оставшуюся потребность (`SetRemainingSize`) и получают fair-резервирование ≈ `min(60% лимита / active_count, need)`, с `SetMinimumReservation` в качестве нижней планки от голодания. Резервирования пересматриваются при добавлении/завершении операторов; оператор, чьё резервирование меньше размера данных, переключается на партиционированный/out-of-core алгоритм. Реализовано для hash join и radix-партиционированной агрегации.

Ключевые ссылки: <https://duckdb.org/2024/07/09/memory-management>, <https://github.com/duckdb/duckdb/pull/10147>, <https://duckdb.org/2024/03/29/external-aggregation>.

## 6\. Apache DataFusion

`MemoryPool` — это trait; операторы вызывают `try_grow()` перед аллокацией и обязаны выполнить спиллинг и повторить попытку при отказе. Реализации:

  - **GreedyMemoryPool** — единый атомарный счётчик, FCFS, без справедливости.
  - **FairSpillPool** — делит потребителей на неспиллируемых (FCFS) и spillable; резервирование каждого spillable-потребителя ограничено `(pool_size − unspillable_memory) / num_spillable_reservations`. Пул никогда не командует спиллингом — он только отказывает в росте; оператор сам выполняет спиллинг. Известный режим отказа (issue \#17334): неспиллируемый оператор может испытывать голодание, когда spillable-операторы реактивно потребляют — свидетельство того, что *только-отказывающая* справедливость без арбитража нестабильна.
  - **TrackConsumersPool** — декоратор, аннотирующий ошибки OOM с топ-потребителями по имени и байтам (дёшево, высокая диагностическая ценность).

Ключевые ссылки: <https://docs.rs/datafusion/latest/datafusion/execution/memory_pool/>, <https://github.com/apache/datafusion/issues/17334>.

## 7\. Trino / Presto

### 7.1 Отказ → блокировка, и смерть reserved pool

Исторический двухпульный дизайн Presto (general + reserved, куда на всех воркерах под давлением мигрировал единственный крупнейший запрос) был **удалён** в Trino (\#6677): кластерная миграция вызывала непредсказуемые скачки памяти и была лишь подпоркой. Что осталось:

  - Лимиты на воркер для пользователя и итоговые (`query.max-memory-per-node`, `query.max-total-memory-per-node`) и кластерные агрегаты (`query.max-memory`), плюс явный `memory.heap-headroom-per-node` для неотслеживаемых JVM-аллокаций.
  - **Заблокированное состояние**: task, которому не хватает памяти, *блокируется* (перестаёт потреблять CPU, ждёт освобождения памяти) вместо немедленного отказа.
  - **OOM killer** как выход из дедлока: `query.low-memory-killer.policy` = `total-reservation` (убить кластерно крупнейший запрос) или `total-reservation-on-blocked-nodes` (убить retryable tasks на узлах, которые реально исчерпали память). Одно убийство на событие, затем переоценка.
  - Память делится на user / system / **revocable** (spillable)-категории; revocable-память учитывается против итогового, но не пользовательского лимита.

### 7.2 Ресурсные группы: ворота допуска по памяти без убийств

`softMemoryLimit` на ресурсную группу: когда суммарное потребление группы превышает его, **новые запросы встают в очередь**; выполняющиеся запросы не затрагиваются. В сочетании с `hardConcurrencyLimit`, `maxQueued` и взвешенными/fair-политиками планирования. Это чётко разделяет «контроль допуска (admission control) по бюджету памяти» и «применение лимита через убийство».

Ключевые ссылки: <https://trino.io/docs/current/admin/resource-groups.html>, <https://trino.io/docs/current/admin/properties-memory-management.html>, <https://github.com/trinodb/trino/issues/6677>, <https://prestodb.io/blog/2019/08/19/memory-tracking/>.

## 8\. Apache Impala

Иерархия MemTracker (process → query → fragment → operator) с **двумя величинами на узел: consumption и reservation**. Отличительная часть — контроль допуска:

1.  Планировщик оценивает память на хост по статистике таблиц; admission зажимает её в диапазон пула `[min-query-mem-limit, max-query-mem-limit]`.
2.  Admission проверяет суммарный `max-memory` пула **включая резервирования допущенных, но ещё не голодных запросов** — это предотвращает thundering herd, когда многие запросы, допущенные на основе текущего потребления, начинают аллоцировать одновременно.
3.  Каждый блокирующий оператор обязан получить своё **минимальное буферное резервирование** (достаточное для работы даже при интенсивном спиллинге) заранее; если ни один исполнитель не может его выдать, запрос *отклоняется на admission*, а не допускается и затем убивается в процессе.
4.  В противном случае запросы **встают в очередь** (`max-queued-queries`, `queue-timeout-ms`).

Ключевые ссылки: <https://impala.apache.org/docs/build/html/topics/impala_admission.html>, <https://impala.apache.org/docs/build/html/topics/impala_buffer_pool_limit.html>.

## 9\. SQL Server

### 9.1 Гранты памяти и resource semaphore

Оптимизатор вычисляет **минимальный** и **желаемый** грант памяти на запрос. Гранты выдаются из *resource semaphore* пула: если памяти нет — запрос **ждёт** (`RESOURCE_SEMAPHORE`) до cost-based таймаута, может быть деградирован до минимального гранта (выполнение с интенсивным спиллингом) и получает ошибку (8645/8657) лишь как крайняя мера. Пулы Resource Governor имеют `MIN/MAX_MEMORY_PERCENT`; группы воркloadов ограничивают долю отдельного запроса (`REQUEST_MAX_MEMORY_GRANT_PERCENT`, по умолчанию 25% пула) — и движок сначала *снижает DOP* для уменьшения требования, прежде чем отказать.

### 9.2 Адаптивная обратная связь по гранту памяти

Постисполнительная обратная связь корректирует оценку для будущих выполнений того же плана: спиллинги → грант увеличивается; грант >2× использованного → уменьшается; с SQL Server 2022 обратная связь основана на перцентилях и **сохраняется в Query Store**, переживая вытеснение кэша планов. Обратная связь никогда не превышает ограничение группы воркloada.

Ключевые ссылки: <https://learn.microsoft.com/en-us/sql/relational-databases/performance/intelligent-query-processing-memory-grant-feedback>, <https://learn.microsoft.com/en-us/sql/t-sql/statements/create-workload-group-transact-sql>.

## 10\. Greenplum / Cloudberry

Ресурсные группы с **фиксированным + общим** разделением памяти каждой группы: каждая транзакция получает гарантированный срез (`MEMORY_QUOTA / CONCURRENCY`); общая часть (`MEMORY_SHARED_QUOTA`, по умолчанию 80%) предоставляется по FCFS в burst-режиме. `MEMORY_SPILL_RATIO` задаёт, при каком уровне в рамках бюджета операторы начинают спиллинг. Учёт осуществляется **Vmem tracker'ом**, перехватывающим каждый `palloc()` в процессе, с глобальным ограничением `gp_vmem_protect_limit`. **Детектор runaway** активируется при `runaway_detector_activation_percent` (90% по умолчанию) от потолка узла и убивает наибольших потребителей до снижения ниже порога (системная группа освобождена). Admission ставит транзакции в очередь при недоступности слотов параллелизма или срезов памяти.

Ключевые ссылки: <https://techdocs.broadcom.com/us/en/vmware-tanzu/data-solutions/tanzu-greenplum/7/greenplum-database/admin_guide-workload_mgmt_resgroups.html>.

Сходящиеся выводы по всем десяти системам:

1.  **Никто не наказывает первого обратившегося на уровне узла.** Каждая система, выжившая в production под нагрузкой, разрешает *глобальное* давление через выбор жертвы (наибольший сверх гарантии или наибольший по абсолютному значению), ожидание или арбитраж — но никогда не отказывает тому запросу, который просто аллоцировал следующим. CockroachDB, единственная система без этого, описывает бури «memory budget exceeded» как известную проблему. YDB сегодня работает по принципу «первый обратившийся падает» — и на уровне пула, и на уровне узла.
2.  **Двухуровневые лимиты универсальны**: мягкий порог, изменяющий *поведение* (спиллинг, throttle, сжатие), и жёсткий порог, изменяющий *исход* (отмена). Мягкий уровень — на оператор или как доля от лимита; жёсткий — на запрос/пул/узел.
3.  **Ворота admission по памяти работают, а убийство в процессе выполнения — запасной вариант, а не основной сценарий.** Trino/Impala/SQL Server/Greenplum — все ставят admission на gate по памяти пула (резервирования, а не только потребление); системы без этого (TiDB, ClickHouse до воркloadов) вынуждены были добавлять аварийные «убить наибольшего потребителя».
4.  **Арбитраж (Velox) — это передний край**: логическая ёмкость перемещается между выполняющимися запросами, изымается через спиллинг по внешней команде, а прерывание используется только в крайнем случае. Это требует, чтобы операторы сообщали `reclaimableBytes()` и реализовывали точку входа reclaim — контракт, а не переписывание.
5.  **Все сверяют отслеживаемые байты с видом аллокатора/ОС** — через явный carve-out (конфиг headroom) или цикл коррекции (MemoryWorker, cgroup observers, тюнеры GOMEMLIMIT).

## 12\. Переносимые идеи и рекомендации для YDB

Упорядочены по влиянию на план (`workload_manager_memory_limits_plan.md`); каждая привязана к шагу плана или предлагает новый follow-up. Все — предложения уровня документа, код не затронут.

### R1. Гарантированная vs burst-память на ресурсный пул (denominator ClickHouse + fixed/shared Greenplum)

Дать каждому ресурсному пулу **гарантию памяти** (выводимую из `RESOURCE_WEIGHT` или нового `MEMORY_GUARANTEE_PERCENT_PER_NODE`) наряду с существующим лимитом. Инвариант: сумма гарантий ≤ бюджет узла ≤ сумма лимитов (overcommit между гарантией и лимитом допускается). Давление между пулами тогда разрешается по чётко определённому ранжированию: `used / guarantee`. → Расширяет шаг 5 плана (модель данных арбитра) и шаг 11 (взвешенный admission); та же пара guarantee/limit — это то, к чему сошлись ClickHouse, Greenplum и SQL Server (MIN/MAX\_MEMORY\_PERCENT).

### R2. Выбор жертвы вместо отказа первому обратившемуся на уровне узла (ClickHouse, TiDB, Trino, Greenplum)

Сегодня при исчерпании `TotalMemoryResource` запрос, обратившийся следующим, получает отказ — вне зависимости от того, кто создал давление. Добавить узловой проход арбитра: когда запрос не может быть удовлетворён, ранжировать выполняющиеся запросы по (приоритет пула, `used/guarantee`, размер) и отменять — или сначала попросить уменьшиться/спиллировать (R3) — наибольшего потребителя, пока запрашивающий ждёт с таймаутом (асинхронно, через mailbox актора — ни в коем случае не блокируя поток). Вести **кольцевой буфер аудита** событий kill/deny (аналог `MEMORY_USAGE_OPS_HISTORY` TiDB), отображаемый на странице mon RM. → Это наибольшее доступное поведенческое улучшение; встраивается в шаг 5 плана. Под feature-флагом, по умолчанию выключен изначально (та же дисциплина выкатки, что и D-решения плана).

### R3. Цепочка эскалации при пути отказа в квоте (OOMAction TiDB; reclaim Velox)

Заменить бинарный результат «выдано / не выдано» `IMemoryQuotaManager::AllocateQuota` упорядоченной эскалацией, которую вычислительная сторона уже частично реализует:

1.  **спиллинг** — `IsReasonableToUseSpilling` уже существует; сделать так, чтобы отказ *сначала* устанавливал hint на спиллинг и повторял попытку;
2.  **сжатие** — попросить актора `TryShrinkMemory` (освободить свободные страницы, снизить лимит);
3.  **ожидание** — ограниченное асинхронное ожидание квоты (заблокированное состояние Trino / semaphore SQL Server), зарегистрированное в RM как memory waiter, пробуждаемое по `FreeQuota` от завершающихся запросов;
4.  **отказ** — типизированное `TMemoryLimitExceededException` (никогда не `yexception` — риск по §6 плана). Шаги 1–2 дёшевы и локальны; шаг 3 — новый механизм под feature-флагом; шаг 4 — текущее поведение, остаётся терминальным состоянием. → Уточняет шаги 5–6 плана; структура цепочки означает, что каждый этап может быть выпущен отдельным тикетом.

### R4. Ворота admission по резервированиям памяти пула, а не потреблению (Impala, softMemoryLimit Trino)

Admission в workload service (уже основанный на очереди для параллелизма) должен также проверять: `pool.reserved_memory + query_initial_grant ≤ pool.memory_limit`, где `reserved` учитывает допущенные-но-ещё-не-аллоцированные гранты (разграничение reservation/consumption в Impala — предотвращает thundering herd одновременно допущенных запросов). Превышение мягкого лимита → новые запросы встают в существующий FIFO пула; выполняющиеся запросы не затрагиваются (семантика Trino). → Усиливает шаг 11 плана точной семантикой и переиспользует очередь workload service вместо создания новой.

### R5. Оценка начального гранта с обратной связью выполнения (адаптивные гранты SQL Server)

Проверка admission в R4 требует размера гранта на запрос. Начать со статического значения, выводимого из `QUERY_MEMORY_LIMIT_PERCENT_PER_NODE`, затем добавить цикл обратной связи: записывать пиковую отслеживаемую память на форму запроса (KQP уже вычисляет хеш запроса для кэша скомпилированных запросов) и использовать высокий перцентиль последних выполнений как грант следующего admission, зажатый в диапазон min/max пула (ограничения Impala). История SQL Server показывает, что подход на основе перцентилей лучше, чем на основе последнего выполнения (осцилляции). → Новый follow-up тикет (§5 плана); зависит от счётчиков шага 2 + охвата шага 7.

### R6. Целевая эволюция арбитра: двухфазный reclaim перед прерыванием (Velox SharedArbitrator)

Долгосрочный облик арбитра памяти плана: при запросе роста, превышающем бюджет пула/узла — (а) изъять *свободную* квоту (выданную, но неиспользуемую; `TryShrinkMemory` делает это реальным) у других запросов, только бухгалтерски; (б) скомандовать спиллинг кандидатам, ранжированным по reclaimable bytes (вычислительные акторы уже знают размер spillable-состояния; добавить `reclaimableBytes` в snapshot RM); (в) только тогда прерывать по ранжированию R2. Требует двух контрактов, которые акторы должны реализовать: сообщать reclaimable bytes; обрабатывать асинхронное событие «освободить N байт». `nonReclaimableSection` Velox соответствует фазам, в которых актор не может спиллировать (в процессе построения хеш-таблицы) — флаг в snapshot'е. → Это «новый способ», который искал обзор: он превращает память из ресурса «выдать один раз, затем падать» в непрерывно арбитрируемый, аналогично тому, как планировщик CPU уже обращается с CPU. Заложить это в интерфейсы шага 5 сейчас (даже если фазы (б)/(в) выйдут позже), чтобы API арбитра не требовал ломающих изменений.

### R7. Батчинг атрибуции для точного отслеживания через аллокатор (max\_untracked\_memory ClickHouse)

Шаг 12 плана (точное отслеживание через аллокатор) должен использовать паттерн TLS-батча: дельта-счётчик на актор/поток, сбрасываемый в счётчик пула при достижении порога (начать с 4 МБ как в ClickHouse; сделать config-knob, так как это компромисс между точностью применения лимитов и конкуренцией). Это также ответ на опасение плана о конкуренции за счётчики в `MemoryNamedPools` (absl map за мьютексом): батчинг у источника вместо шардирования хранилища.

### R8. Пороги спиллинга как доля от эффективного лимита (PR \#71406 ClickHouse)

Там, где существуют пороги спиллинга (`SpillingPercent` cookies), определять их как долю от *наиболее ограничивающего* лимита в цепочке (грант запроса, лимит пула, бюджет узла), пересчитываемую при изменении грантов, — а не в абсолютных байтах. Автоматическое масштабирование при изменении размера инстанса. → Небольшая правка шага 6.

### R9. Паритет диагностики (TrackConsumersPool DataFusion, дампы аварийного сигнала TiDB)

Дёшево, высокая ценность, можно выпустить рано:

  - Аннотировать каждое `TMemoryLimitExceededException` (и собираемый из него OVERLOADED issue) топ-N потребителями соответствующего пула (имя, байты) на момент отказа.
  - Аварийный сигнал давления при \~70% бюджета узла, записывающий топ-запросы по отслеживаемой памяти в логи (rate-limited), *до* OOM.
  - История аудита R2 на странице mon. → Включить в шаг 2 плана (счётчики) и шаг 9 (mon/observability).

### Явно *не рекомендуется*

  - **Reserved pool в стиле Presto** — удалён выше по течению как ошибка дизайна (\#6677); не изобретать заново в виде «аварийного пула на узел».
  - **Throttling выполняющейся работы с учётом памяти как замена admission** — технические заметки CockroachDB по admission объясняют, почему замедление выполняющейся работы может *увеличить* удержание памяти; сохранять admission (R4) и арбитраж выполняющихся запросов (R6) как отдельные механизмы.
  - **Раскомментирование исторического throw в `dq_compute_memory_quota.h`** — без изменений относительно плана: путь отказа должен оставаться типизированным; R3 формализует то, что происходит *до* типизированного отказа.

## 13\. Стресс-тест масштабирования: какие подходы выживают при устойчивом инjesте \~300 МБ/с на узел

Результаты обзора нужно читать с оговоркой: **в большинстве рассматриваемых систем менеджер памяти никогда не находится на горячем пути ингестии с такой скоростью** — либо путь записи обходит трекер, либо система упирается в другое (планировщик, координатор, диск, GC) до того, как проявятся собственные ограничения масштабируемости менеджера памяти. Ниже: математика событийной скорости для цепочки YDB при 300 МБ/с/узел, затем — какие заимствованные механизмы ломаются первыми и почему система-донор этого никогда не замечала.

### 13.1 Бюджет событийной скорости для цепочки YDB при 300 МБ/с

Предположим \~1 КБ строки → \~300 К строк/с/узел; потоки данных KQP работают кусками \~48 КБ–1 МБ; page pool выдаёт ≥1 МиБ (`MinMemAllocSize` = 30 МиБ первый грант, 1 МиБ выравнивание после).

| Путь                                                              | Гранулярность операции   | Операций/с при 300 МБ/с                       | Вердикт                                                                                                                                                                                               |
| ----------------------------------------------------------------- | ------------------------ | --------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Запросы extra-memory у page pool (`RequestExtraMemory`)           | ≥1 МиБ (30 МиБ первый)   | ≤300/с в худшем случае, \~10/с типично         | Тривиально. Батчинг ≥1 МиБ, уже заложенный в `TDqMemoryQuota` — это наиболее нагруженное свойство дизайна; конкуренция за мьютекс арбитра при такой скорости несущественна.                           |
| `TryAcquire` арбитра (шаг 5), та же гранулярность                | ≥1 МиБ                   | ≤300/с                                        | Один мьютекс достаточен; шардирование не нужно.                                                                                                                                                       |
| Проверки admission (шаг 11 / R4)                                  | на statement              | = скорость statements: 3–50 К/с для small upserts | **Рискованно, если добавляет actor round-trip на statement.** Нужен lock-free быстрый путь: проверять атомарный snapshot `pool.reserved` локально, переходить на путь очереди только при приближении к \~10% от мягкого лимита. |
| Acquisitions буфера/write-актора (шаг 7)                          | на chunk, 48 КБ–1 МБ     | 300–6 000/с                                   | OK **только при chunk-размере acquisitions**. | Отслеживание на уровне аллокатора (шаг 12) через malloc hooks, без батчинга | на аллокацию  | миллионы/с                                    | Не работает. Математика перерасхода для любого *реактивного* механизма: `overshoot ≈ ingest_rate × reaction_latency`. При 300 МБ/с: отказ в момент аллокации (сегодняшнее типизированное исключение) ≈ 0 перерасхода; событийно-управляемое убийство жертвы с задержкой отмены \~100 мс ≈ 30 МБ; цикл опроса 1 с (TiDB-подобный контроллер, RSS workers, реконфигурация RB limit) ≈ **300 МБ за интервал** — запас между мягким порогом и жёстким лимитом узла должен быть не меньше `rate × (poll + cancel latency)`, иначе защитная сетка срабатывает после того, как сработает OOM killer ядра.

### 13.2 Почему каждая система-донор никогда не упиралась в эти ограничения — и что сломается при наивном копировании

  - **ClickHouse** действительно выдерживает сотни МБ/с ингестии через свой трекер — но только благодаря двум свойствам: TLS-батчинг 4 МБ (без него атомарные операции цепочки родителей при миллионах ops/s рухнули бы на конкуренции за cache-line) и путь вставки, состоящий из немногих крупных колоночных буферов, а не многих мелких аллокаций. Что *не переносится*: ожидание overcommit **блокирует OS-поток** на каждый застопоренный запрос. CH терпит это, потому что вставки редко входят в overcommit (память insert-блока ограничена); при тысячах параллельных мелких upsert'ов в стопе, блокирующее ожидание исчерпало бы пул потоков. В YDB ожидание D11 должно быть приостановкой mailbox — это не оптимизация, а требование выживаемости.
  - Контроллер kill-top-consumer **TiDB** *опрашивает* Go `HeapInuse`, и отмена приходит асинхронно спустя секунды; его запас (убивать при 80% RAM, сигнализировать при 70%) неявно рассчитан на скорости ингестии TiDB, которые упираются в планировщик/RPC-слой задолго до 300 МБ/с/узел отслеживаемого чёрна. При наивном переносе в YDB контроллер на основе опроса при 300 МБ/с исчерпает весь запас за один интервал. Преимущество YDB: применение лимитов *управляется аллокацией* (callback page pool), поэтому первичный лимит имеет нулевую задержку реакции — держать контроллер на основе опроса строго как второй уровень защиты и задавать его порог по формуле перерасхода.
  - **SharedArbitrator Velox** сериализует весь арбитраж под глобальным мьютексом, а reclaim означает секунды I/O спиллинга, пока запрашивающий ждёт. Это работает, потому что Prestissimo выполняет *немного, но долгих* аналитических запросов — арбитраж редок. При 3–50 К мелких statements/с любой дизайн, где обычный запрос роста может войти в глобальный арбитраж, сериализовал бы узел. Правило переноса: арбитраж должен входить только выше порога размера (например, запросы сверх гарантии пула) и быть rate-limited; мелкие запросы ниже гарантии следуют быстрому пути grant/deny. Именно поэтому план оставляет фазы (б)/(в) R6 отложенными за интерфейсами D12, а не на первичном пути выдачи.
  - Ворота admission **Trino/Impala/SQL Server** выживают при высоком QPS, потому что ворота — это in-memory проверка semaphore/счётчика (SQL Server обрабатывает 10⁴+ grants/с), *а не* message hop. Их слабость при масштабировании другая: агрегация координатора/statestore запаздывает на heartbeat (Impala явно документирует гонки перехода-допуска между демонами). Узловое применение лимитов YDB не наследует этот изъян — но очередь workload service не должна стать actor round-trip на statement (быстрый путь выше).
  - **TemporaryMemoryManager DuckDB** пересматривает доли под мьютексом *по всем* зарегистрированным состояниям при каждом join/leave — идеально для ≤десятков крупных операторов во встроенном процессе, квадратичная нагрузка при тысячах параллельных регистраций/с. Использовать формулу fair share для немногих крупных spillable-потребителей (на пул), никогда — как механизм регистрации на запрос.
  - Перехват Vmem `palloc` **Greenplum** на *каждую* аллокацию стоит дорого; GP терпит это, потому что ингестия сегмента упирается в dispatch/сеть. Это поучительная история для шага 12 без батчинга.
  - **CockroachDB** — наиболее поучительная параллель для вопроса *охвата*: его путь ингестии (KV/Pebble memtable) полностью обходит дерево SQL BytesMonitor — SQL memory manager просто не видит давления bulk-write, а защита узла обеспечивается раздельно бюджетируемыми memtable/кэшем плюс запасом. См. 13.3.

### 13.3 Честные выводы, специфичные для YDB

1.  **Разрыв охвата — это реальный риск 300 МБ/с, а не пропускная способность менеджера.** При высоких скоростях ингестии большинство давления памяти живёт *вне* квот вычислений KQP до тех пор, пока не появятся шаги 7–9: буферы событий interconnect, in-flight очереди write-акторов, буферы вставки и компакции datashard/columnshard (потребители Memory Controller). Как SQL-монитор CockroachDB, лимиты воркload-менеджера будут точны для вычислений и *слепы к ингесту* в переходный период — лимиты пула могут выглядеть зелёными, пока узел падает по OOM от памяти пути записи. Следствие: (а) индикатор managed-vs-total шага 2 нужно отдельно наблюдать под write-heavy нагрузкой, (б) ворота admission (R4) не должны позиционироваться как защита узла от OOM до тех пор, пока охват пути записи шагом 7 не появится, (в) вторичная узловая защитная сетка (R2) должна опираться на целопроцессный вид Memory Controller (RSS/soft limit), а не на сумму счётчиков пулов.
2.  **Дизайн с выдачей кусками — это то, что делает всё остальное доступным.** Гранулярность гранта ≥1 МиБ ограничивает трафик арбитра до \~300 ops/с даже при 300 МБ/с — решения могут оставаться за одним мьютексом, ранжирование жертв может быть точным, аудит-логгирование бесплатно. Сохранять этот инвариант в шаге 7: каждый новый учитываемый путь должен делать acquisitions в chunk-размере с батчингом на уровне актора, иначе он станет новым узким местом.
3.  **Пути давления нуждаются в storm control, а не только в корректности.** При устойчивом насыщении (ингест бесконечно выше бюджета) эпизоды deny/victim/wait повторяются непрерывно: пробуждения ожидающих по каждому `FreeQuota` должны происходить в порядке гранта и батчами (thundering herd), выбор жертвы должен быть rate-limited (одно убийство на эпизод, затем переоценка — семантика Trino), и цепочка эскалации (R3) должна помнить на запрос, что spill/shrink уже потерпели неудачу, а не перезапускать цепочку на каждом 1 МиБ-запросе.
4.  **Быстрый путь должен оставаться одной атомарной проверкой.** При 300 МБ/с настоящим ограничением узла может быть диск, компакция или interconnect — управление памятью никогда не должно быть тем, что первым появляется в flamegraph. Бенчмарк-ворота (§4 плана) должны включать сценарий write-насыщения: bulk upsert ≥300 МБ/с при включённых лимитах vs без них, с утверждением <1% потерь пропускной способности ингестии, наряду с существующим сценарием TPC-C + OLAP-scan.

**SafeLoad — за чем следить.** Их pipeline: (1) интерпретируемое пороговое правило («\#joins > 1 ИЛИ \#windows > 0, И scan output > 1 МБ, И вчера в кластере был OOM») обрабатывает 97.8% запросов за 401 нс; (2) XGBoost-модели на кластер (кластеры с ≥100 MO-примерами; глобальная модель иначе) по 163 plan+cluster features; (3) FAISS-индекс прошлых false negative перехватывает повторяющиеся сбои (cosine ≥ 0.9999); (4) энтропийно-ценоопределяемая квота на позитивные предсказания на кластер — их единственный наибольший рычаг точности (0.55 → 0.81; +66% max vs лучший baseline; 8.09× меньше впустую потраченного CPU).

  - **Порядок работы подтверждён.** SafeLoad — только admission: false negative всё равно приводит к OOM (recall 0.89 → \~11% MO-запросов всё равно приземляются) и просто записывается для следующего раза; защитная сетка — перенаправление в оплачиваемые провайдером serverless-кластеры. У YDB нет такого overflow-уровня и узлы делятся между тенантами, поэтому runtime-применение лимитов (шаги 4–7 плана) должно быть первым; предсказание — оптимизация поверх, а не замена.
  - **Классификация вместо регрессии.** Они показывают, что *регрессия* пиковой памяти — неверный инструмент для admission (baseline регрессии F1 ≤ 0.38; пики транзиентны, доступная память меняется между отправкой и выполнением). Умеряет R5: перцентильная обратная связь по грантам — для *начального размера*, а не для вердиктов admission.
  - **Стадирование rule-before-ML подходит.** Эквивалентное дешёвое правило может работать в workload service с нулевой ML-инфраструктурой в той же точке вставки, где `DatabaseLoadCpuThreshold` уже ставит ворота (после компиляции, до исполнения). Их ключевая feature — «OOM-события в этом кластере вчера» — соответствует per-pool счётчикам `DeniedRequests`/OOM: счётчики шага 2 и статистика на запрос шага 6 должны быть запрашиваемы (system view), а не только сенсорами, чтобы впоследствии служить features и labels.
  - **Асимметрия FP/FN.** Для них false positive расходует квоту пользователя; для YDB ложное «будет перегружена» означало бы отказ/очередь для безопасного запроса — видимо пользователю. Любой будущий auto-deny должен копировать их квотируемые позитивы (ограниченная скорость предсказание-driven отказов).
  - **SafeBench** (150М production-запросов, github.com/SafeLoad-project/SafeBench) пригоден как внешний корпус валидации для прототипа предиктора YDB.

**Обзор buffer management — за чем следить.** Память кэша упруга и вытесняема; рабочая память запроса — это occupancy — разные контуры управления. Это подтверждает, что разделяемые кэши нужно держать под Memory Controller (вне целей дизайна), а не включать в арбитр. Балансировка бюджета с обратной связью/utility-driven из обзора — это правдоподобная более поздняя эволюция бинарного consumer split Memory Controller; она достигнет арбитра только через существующий канал RB queue-limit (вывод 1.3.2 плана), поэтому изменений интерфейса арбитра не требуется. Уровни спиллинга на disaggregated memory/NVM — долгосрочный вариант для D5: чем дешевле спиллинг, тем агрессивнее может быть spill-first (R3).

**Статья NVM — за чем следить.** Её helper-потоки, делающие prefetch от имени запроса, — это в точности случай кросс-поточной атрибуции, который event context шага 9 плана и `TMemoryContextGuard` должны поддерживать — оставить это требование первоклассным. Её результаты усиливают тот же тренд дешёвого спиллинга, что и выше.
